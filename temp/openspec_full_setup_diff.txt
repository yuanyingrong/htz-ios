+# Active Risks
+
+## 🔴 Critical Risks
+
+### 1. FreeStreamer Lifecycle Risk
+- **Description**: `FreeStreamer` is an Objective-C/C library with manual memory management.
+- **Risk**: Wrapping it in a Swift Actor might lead to race conditions if the C-callbacks interact with Main Thread objects inappropriately, or memory leaks if closures capture the streamer incorrectly.
+- **Mitigation**: Use `CheckedContinuation` carefully and ensure all UI updates from the actor are dispatched via `MainActor`.
+
+### 2. HTZPlayViewController Complexity
+- **Description**: This class is deeply intertwined with almost all app systems (Audio, UI, Network, Share).
+- **Risk**: Attempting to refactor it too early or all at once will break core App functionality.
+- **Mitigation**: This must be the **last** page migrated. We will extract its logic into TCA actions gradually, first as dependencies.
+
+## 🟠 High Risks
+
+### 3. TCA Scope Creep
+- **Description**: TCA can become overly complex if state is shared unnecessarily across deep trees.
+- **Risk**: Creating a monolithic "Global State" that makes the App sluggish or hard to maintain.
+- **Mitigation**: Keep features scoped. Use `Shared` state only where absolutely necessary (e.g., Now Playing).
+
+### 4. SwiftUI/UIKit Navigation Hybrid Risk
+- **Description**: Managing a stack that mixes `UINavigationController` and `NavigationStack`.
+- **Risk**: Broken back buttons, navigation bar double-headers, or memory leaks from unreleased View Controllers.
+- **Mitigation**: Strictly use `UIHostingController` and `UIViewControllerRepresentable` with clean deinit logic.
+
+### 5. Design System Inconsistency
+- **Description**: The team might bypass tokens for "quick fixes."
+- **Risk**: UI becoming fragmented again, defeating the purpose of the refactor.
+- **Mitigation**: Code reviews must enforce token usage. No raw `Color` or `Font` initializers in Features.

+# ADR-001: Use The Composable Architecture (TCA)
+
+## Status
+Accepted
+
+## Context
+The legacy application suffers from "God Views" (e.g., `HTZPlayViewController`), heavy use of singletons, and fragmented communication patterns (Delegates, Notifications, didSet). This makes state synchronization difficult and testing nearly impossible.
+
+## Decision
+Adopt **The Composable Architecture (TCA)** as the primary state management framework for the modernized application.
+
+## Rationale
+1. **Unidirectional Data Flow**: Ensures state changes are predictable and easy to debug.
+2. **Testability**: Provides `TestStore` for exhaustive unit testing of business logic.
+3. **Modularity**: Naturally supports feature decomposition and composition.
+4. **SwiftUI First**: Deeply integrated with SwiftUI's state management primitives.
+5. **Standardization**: Reduces developer cognitive load by providing a consistent pattern for all features.
+
+## Consequences
+- Requires a learning curve for developers unfamiliar with functional programming or Redux-like patterns.
+- Adds boilerplate for simple features.
+- Tight coupling with the TCA library (mitigated by its widespread adoption and stability).

+# ADR-002: Use SPM for Internal Modularization
+
+## Status
+Accepted
+
+## Context
+The legacy project is a monolithic Xcode target using CocoaPods for all dependencies. This leads to slow build times, tight coupling, and difficulty in isolating feature-specific logic.
+
+## Decision
+Use **Swift Package Manager (SPM)** to create internal modules for business logic, UI components, and core services.
+
+## Rationale
+1. **Compilation Isolation**: Faster incremental builds as unchanged packages aren't recompiled.
+2. **Clear Boundaries**: Forces developers to define explicit interfaces between modules.
+3. **Swift Native**: No extra tools required for internal dependency management.
+4. **Testing**: Easier to write and run unit tests for isolated modules.
+
+## Consequences
+- Requires maintaining a root `Package.swift`.
+- Coexistence with CocoaPods for legacy external SDKs (JPush, JShare) is necessary during the transition.
+- Need to manage visibility (`public` vs `internal`) across module boundaries.

+# ADR-003: SwiftUI Incremental Migration Strategy
+
+## Status
+Accepted
+
+## Context
+The App is 100% UIKit with SnapKit. A full "big bang" rewrite is too risky.
+
+## Decision
+Adopt an **"Inside-Out" Incremental Migration Strategy**.
+
+## Rationale
+1. **Low Risk**: Start with simple leaf pages (Profile, Login) to establish the pattern.
+2. **Hybrid State**: Use `UIViewControllerRepresentable` and `UIHostingController` to bridge legacy and modern components.
+3. **Iterative Value**: Deliver modernized features while keeping the rest of the App functional.
+4. **Learning Loop**: Refine the design system and TCA patterns on simpler pages before tackling the complex Player page.
+
+## Consequences
+- Requires temporary "bridge" code (converters, wrappers).
+- Navigation logic will be complex during the hybrid phase (UIKit Nav vs SwiftUI NavigationStack).
+- UI inconsistency might occur if the design system isn't strictly followed in hybrid views.

+# ADR-004: Player Actor Wrapper
+
+## Status
+Accepted
+
+## Context
+The core audio engine uses `FreeStreamer` (Objective-C/C), which is not thread-safe and is accessed via global singletons. This causes race conditions and UI freezing.
+
+## Decision
+Wrap the legacy `FreeStreamer` engine in a **Swift Actor** (specifically a `@globalActor`).
+
+## Rationale
+1. **Concurrency Safety**: Actors provide compiler-guaranteed data isolation.
+2. **Modern API**: Exposes an async/await interface to the rest of the App.
+3. **Decoupling**: Decouples audio logic from UIKit view controllers.
+4. **Preservation**: Avoids the massive effort and risk of rewriting the low-level C/OC streaming logic.
+
+## Consequences
+- Requires bridging C-callbacks to Swift async continuations.
+- UI must observe state via `AsyncStream` or `MainActor`-safe publishers.
+- Potential performance overhead for high-frequency progress updates (mitigated by throttling).

+# ADR-005: Design System Token Strategy
+
+## Status
+Accepted
+
+## Context
+UI styling is currently hardcoded in ViewControllers using raw colors and magic numbers for spacing/radius.
+
+## Decision
+Implement a **Centralized Token System** within a dedicated `DesignSystem` SPM module.
+
+## Rationale
+1. **Consistency**: Ensures all new SwiftUI views use the same colors, fonts, and spacing.
+2. **Maintenance**: Allows project-wide style changes (e.g., brand color update) by editing a single file.
+3. **Dark Mode**: Simplifies Dark Mode support through semantic color naming.
+4. **Developer Experience**: Auto-completion for tokens reduces errors and speeds up UI development.
+
+## Consequences
+- Requires a one-time effort to define and map all tokens.
+- Legacy UIKit views won't automatically benefit unless manually refactored to use the tokens (via bridge extensions).
